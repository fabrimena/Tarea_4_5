\begin{abstract}
Este informe documenta el prototipo funcional desarrollado como primera entrega del proyecto de sistema multi-agente para el curso de Inteligencia Artificial del Instituto Tecnológico de Costa Rica. El sistema implementado integra un agente orquestador basado en GPT-4o, una canalización RAG (\textit{Retrieval-Augmented Generation}) sobre los apuntes del curso almacenados en ChromaDB, un agente de búsqueda web mediante la API de Tavily, un agente resumidor y observabilidad completa a través de Langfuse. Se describe la arquitectura inicial, las decisiones técnicas tomadas, los problemas encontrados durante el desarrollo y el plan de trabajo para incorporar los componentes restantes en la segunda entrega.
\end{abstract}

% ================================================================
\section{Introducción}
% ================================================================

El objetivo del proyecto es construir un sistema multi-agente capaz de responder preguntas académicas apoyándose en los apuntes del curso de Inteligencia Artificial, fuentes externas en internet y, en la segunda etapa, en una base de datos transaccional ficticia. El sistema debe combinar técnicas de RAG, orquestación de agentes, memoria conversacional y observabilidad de trazas.

Esta primera entrega corresponde al prototipo funcional. Se implementaron el agente orquestador, la canalización RAG con ChromaDB, el agente de búsqueda web, el agente resumidor y la observabilidad con Langfuse, además de una interfaz web mínima con Streamlit. En las secciones siguientes se documenta la arquitectura adoptada, las decisiones técnicas relevantes, los problemas encontrados y el plan para la segunda entrega.

% ================================================================
\section{Descripción General de la Arquitectura}
% ================================================================

La arquitectura del prototipo sigue un patrón de orquestación centralizada. Un agente principal (\textit{Orchestrator}) recibe cada pregunta del usuario, decide qué herramienta invocar y sintetiza la respuesta final. La Figura~\ref{fig:arquitectura} resume el flujo general del sistema.

Los componentes principales son:

\begin{itemize}
    \item \textbf{Base documental}: apuntes del curso en formato PDF, preprocesados y almacenados en ChromaDB como vectores de embeddings.
    \item \textbf{Agente Orquestador}: modelo \texttt{gpt-4o}, encargado de seleccionar herramientas y construir la respuesta final.
    \item \textbf{Agente RAG}: modelo \texttt{gpt-4o-mini}, genera respuestas a partir de los fragmentos recuperados de la base vectorial.
    \item \textbf{Agente Web Search}: modelo \texttt{gpt-4o-mini} con la API de Tavily para búsquedas externas.
    \item \textbf{Agente Resumidor}: modelo \texttt{gpt-4o-mini}, genera resúmenes de semanas específicas usando búsqueda vectorial filtrada por metadato.
    \item \textbf{Observabilidad}: Langfuse registra trazas de cada ejecución, incluyendo spans de recuperación, generación y llamadas entre agentes.
    \item \textbf{Interfaz web}: aplicación Streamlit que expone el agente al usuario.
\end{itemize}

\section{Preprocesamiento Textual y Base Documental}
% ================================================================

\subsection{Extracción y limpieza}

Los documentos del dataset provienen de apuntes elaborados por estudiantes del curso, nombrados con la convención \texttt{<semana>\_SEMANA\_AI\_<fecha>\_<número>.pdf}. El proceso de extracción utilizó la librería \texttt{pypdf} para leer cada página. Sobre el texto crudo se aplicaron las siguientes operaciones de limpieza:

\begin{itemize}
    \item Eliminación de caracteres de control y saltos de línea redundantes.
    \item Normalización Unicode para corregir tildes y caracteres especiales del español.
    \item Extracción automática de metadatos a partir del nombre del archivo mediante expresiones regulares: número de semana, fecha de elaboración y número de documento.
\end{itemize}

\subsection{Metadatos extraídos}

Cada fragmento almacenado en la base vectorial incluye los siguientes metadatos:

\begin{table}[htbp]
\caption{Metadatos almacenados por fragmento}
\label{tab:metadatos}
\centering
\begin{tabular}{ll}
\toprule
\textbf{Campo} & \textbf{Descripción} \\
\midrule
\texttt{semana}         & Número de semana del curso (entero) \\
\texttt{fecha}          & Fecha del apunte (\texttt{YYYYMMDD}) \\
\texttt{nombre\_archivo}& Nombre original del PDF \\
\texttt{chunk\_index}   & Índice del fragmento dentro del documento \\
\bottomrule
\end{tabular}
\end{table}

El metadato \texttt{semana} resulta especialmente útil para el agente resumidor, que filtra directamente la colección ChromaDB con \texttt{where=\{"semana": week\}} antes de ejecutar la consulta vectorial.

\subsection{Segmentación}

La estrategia de segmentación utilizada en el prototipo es \texttt{RecursiveCharacterTextSplitter} de LangChain con los siguientes parámetros:

\begin{itemize}
    \item \texttt{chunk\_size = 500} caracteres.
    \item \texttt{chunk\_overlap = 100} caracteres.
\end{itemize}

Esta configuración fue elegida como punto de partida por ser balanceada entre granularidad semántica y costo de embeddings. En la segunda entrega se implementará y comparará una segunda estrategia de segmentación (por ejemplo, segmentación por párrafo o por oración) para evaluar cuál produce mejores resultados de recuperación.

\section{Embeddings y Base Vectorial}
% ================================================================

\subsection{Modelo de embeddings}

Se utilizó el modelo \texttt{text-embedding-3-small} de OpenAI para generar los vectores de los fragmentos. La selección se justifica por los siguientes factores:

\begin{itemize}
    \item \textbf{Disponibilidad}: accesible directamente a través de la API de OpenAI, sin infraestructura adicional.
    \item \textbf{Costo}: es el modelo de embeddings de menor costo en el catálogo de OpenAI.
    \item \textbf{Dimensión}: produce vectores de 1536 dimensiones, compatibles con ChromaDB sin configuración adicional.
    \item \textbf{Soporte multilingüe}: maneja correctamente texto en español.
\end{itemize}

\subsection{Base vectorial}

Se utilizó ChromaDB con almacenamiento persistente en disco (\texttt{PersistentClient}). La colección se denomina \texttt{apuntes\_ai} y los vectores se generan una única vez; en ejecuciones posteriores se reutilizan si la colección ya existe. El umbral de distancia coseno para filtrar fragmentos poco relevantes se fijó en \texttt{MAX\_DISTANCE = 0.6}.

\section{Diseño de Agentes y Responsabilidades}
% ================================================================

\subsection{Agente Orquestador}

El orquestador utiliza el modelo \texttt{gpt-4o} con \textit{function calling}. Recibe la pregunta del usuario y decide, sin intervención manual, qué herramienta invocar. El \textit{system prompt} define tres herramientas disponibles:

\begin{itemize}
    \item \texttt{consultar\_apuntes}: invoca el pipeline RAG.
    \item \texttt{resumir\_semana}: genera un resumen semanal filtrado por metadato.
    \item \texttt{buscar\_en\_web}: ejecuta una búsqueda Tavily cuando la información no se encuentra en los apuntes o el usuario lo solicita explícitamente.
\end{itemize}

Una regla importante en el prompt es el \textit{fallback} automático: si \texttt{consultar\_apuntes} retorna la cadena ``No encontré información suficiente'', el orquestador escala automáticamente a \texttt{buscar\_en\_web} sin pedir confirmación al usuario.

\subsection{Agente RAG}

Implementado en \texttt{rag.py}, este agente recupera los $k=5$ fragmentos más relevantes de ChromaDB, filtra por distancia coseno y construye un contexto que envía al modelo \texttt{gpt-4o-mini}. El prompt instruye al modelo a responder únicamente desde el contexto recuperado, reduciendo alucinaciones.

\subsection{Agente Web Search}

Implementado en \texttt{websearch.py}, este agente llama a la API de Tavily con hasta cinco resultados, construye un contexto con título, URL y fragmento de cada resultado, y genera la respuesta con \texttt{gpt-4o-mini}.

\subsection{Agente Resumidor}

Implementado dentro de \texttt{agent.py} como la función \texttt{summarize\_week}. Realiza una búsqueda vectorial en ChromaDB filtrada por el metadato \texttt{semana} y genera un resumen con el modelo \texttt{gpt-4o-mini}.

\subsection{Contratos de agentes}

A continuación se muestra el contrato mínimo del Agente RAG como ejemplo:

\section{Observabilidad con Langfuse}
% ================================================================

Se integró Langfuse mediante el SDK oficial de Python (\texttt{langfuse.openai}). Cada ejecución del agente crea un \textit{span} raíz llamado \texttt{agent\_run} que anida los siguientes sub-spans:

\begin{itemize}
    \item \texttt{agent\_decision}: captura la llamada de \textit{function calling} al orquestador.
    \item \texttt{tool\_calls}: registra la ejecución de cada herramienta invocada.
    \item \texttt{rag\_pipeline} $\to$ \texttt{retrieve\_documents} $\to$ \texttt{generate\_answer}: trazabilidad interna del pipeline RAG.
    \item \texttt{websearch\_pipeline} $\to$ \texttt{web\_search\_retrieve} $\to$ \texttt{websearch\_generate\_answer}: trazabilidad del agente web.
    \item \texttt{agent\_final\_response}: respuesta sintetizada por el orquestador.
\end{itemize}

Adicionalmente, el pipeline RAG registra tres métricas de calidad por traza: \texttt{context\_relevance} (calculada como $1 - \bar{d}$ donde $\bar{d}$ es la distancia coseno promedio), \texttt{answer\_correctness} y \texttt{groundedness}.

\section{Interfaz Web}
% ================================================================

La interfaz se implementó con Streamlit (\texttt{app.py}). Permite al usuario ingresar una pregunta en un campo de texto y obtener la respuesta generada por el agente junto con los documentos recuperados y sus metadatos desplegados en secciones expandibles. La interfaz es intencionalmente minimalista para esta primera entrega; en la segunda entrega se ampliará para soportar memoria conversacional visible.

\section{Problemas Encontrados}
% ================================================================

Durante el desarrollo del prototipo se encontraron los siguientes problemas:

\begin{enumerate}
    \item \textbf{Calidad de los PDFs}: varios apuntes presentaron texto con codificación irregular o caracteres corruptos tras la extracción con \texttt{pypdf}. Fue necesario aplicar normalización Unicode y eliminar caracteres no imprimibles antes de segmentar.

    \item \textbf{Extracción de metadatos desde el nombre de archivo}: algunos archivos no seguían la convención de nomenclatura esperada (por ejemplo, \texttt{13\_SEMANA\_AI\_2018191805\_1.pdf}), lo que hizo que la expresión regular retornara \texttt{None} para los campos de semana y fecha. Se implementó un manejo de casos por defecto, pero estos documentos se almacenan sin metadato de semana y no pueden ser filtrados por el agente resumidor.

    \item \textbf{Límites de la API de Tavily}: durante pruebas intensivas, la cuenta de Tavily en capa gratuita alcanzó el límite de peticiones, interrumpiendo el flujo del agente web. Se implementó manejo de excepciones que retorna una lista vacía y el orquestador informa al usuario que no se encontraron resultados.

    \item \textbf{Sincronización del contexto de Langfuse}: al ejecutar el agente en múltiples hilos (por la naturaleza de Streamlit), las trazas ocasionalmente se anidaban de forma incorrecta. Se resolvió llamando a \texttt{lf.flush()} al final de cada ejecución de agente para garantizar el envío inmediato.

    \item \textbf{Costo de generación de embeddings}: el proceso inicial de generación de embeddings para todo el dataset tomó varios minutos y generó costos no triviales en la API de OpenAI, consumiendo alrededor de 914k tokens el primer día ya que se regeneraron varias veces debido a malos formateos en el texto de los datos adquiridos de los pdf. Se agregó una verificación que omite la re-generación si la colección ya contiene documentos.
\end{enumerate}

En particular, para los componentes más complejos se describen a continuación las decisiones de diseño tentativas:

\subsection{MCP Server y base transaccional}

Se construirá un servidor MCP usando FastAPI o la librería oficial de MCP para Python. La base de datos relacional se ejecutará en Docker (PostgreSQL) y será poblada con un script Python que genere clientes, cuentas, transacciones normales y transacciones sospechosas siguiendo los patrones definidos en el enunciado. Las herramientas expuestas serán: \texttt{get\_transaction\_by\_id}, \texttt{search\_transactions}, \texttt{get\_customer\_risk\_summary}, \texttt{get\_recent\_flagged\_transactions} y \texttt{create\_fraud\_case}. No se expondrá ninguna herramienta de ejecución SQL libre.

\subsection{Memoria conversacional}

La memoria temporal de sesión se implementará manteniendo el historial de mensajes en la sesión de Streamlit (\texttt{st.session\_state}). La memoria histórica persistente se almacenará en la misma base de datos PostgreSQL, en una tabla de sesiones y mensajes, permitiendo consultas como ``¿qué pregunté anteriormente sobre descenso del gradiente?''.

\section{Conclusiones}
% ================================================================

El prototipo de primera entrega demuestra que la arquitectura base del sistema multi-agente es funcional: el orquestador selecciona correctamente las herramientas, el pipeline RAG recupera fragmentos relevantes desde los apuntes, el agente web complementa la información cuando es necesario y Langfuse registra trazas completas de cada ejecución. Los principales desafíos identificados son la calidad variable de los PDFs fuente, la nomenclatura inconsistente de algunos archivos y los límites de la API gratuita de Tavily. Estos problemas serán abordados en la segunda entrega junto con la incorporación del MCP Server, la base de datos transaccional, la memoria persistente y la evaluación experimental completa.
